Suna Platform Overview
The Suna platform is an open-source system designed for building, managing, and training AI agents, providing capabilities across web, mobile, and backend environments. Its primary purpose is to facilitate the creation of both general-purpose AI assistants, such as the flagship Suna agent, and specialized automation tools. The platform empowers developers to integrate diverse functionalities into their AI agents, including browser automation, file management, web intelligence, system operations, and various API integrations.
Developers can leverage Suna to create AI agents that perform tasks like research and analysis, automate browser interactions, manage files and documents, process and analyze data, and assist with system administration. Beyond these general capabilities, the platform also supports the development of specialized agents tailored for specific domains, such as customer service, content creation, sales and marketing, research and development, and industry-specific applications.
Programmatic interaction with AI Workers on the Suna platform is facilitated through a Python SDK. This SDK provides an interface for managing the lifecycle of AI agents, handling conversational threads, and integrating various tools. For an in-depth understanding of the SDK's capabilities, refer to AI Agent SDK.
The overall architecture of the Suna platform is composed of four main components: the Backend API, the Frontend Dashboard, the Agent Runtime, and the Database & Storage. Each of these components plays a distinct role in enabling the platform's functionality, which is further detailed in Core Architectural Components.
Core Architectural Components
The Suna platform is structured around four primary architectural components that integrate to create an AI agent development and deployment ecosystem. These components are the Backend API, Frontend Dashboard, Agent Runtime, and Database & Storage.
The Backend API serves as the central processing unit of the platform. Implemented in Python using FastAPI, it handles REST endpoints, orchestrates AI agent activities, and integrates with large language models (LLMs). Its responsibilities include managing the lifecycle of AI agents, handling user accounts, and processing billing. It also integrates with external services for various functionalities, such as managing credentials for multi-cloud providers and providing access to tools (e.g., Composio, Google services). Critical system endpoints, such as health checks, are maintained to ensure operational stability. The backend also manages background tasks, such as agent execution, which are run asynchronously to avoid blocking the main API. See Backend Services and AI Agent Management for more details.
The Frontend Dashboard is a Next.js/React application that provides a web-based interface for users to build, configure, and monitor their AI agents. It offers a user-friendly environment for managing agent settings, viewing conversational threads, and interacting with various platform features. The dashboard includes components for user authentication, billing management, knowledge base integration, and an onboarding process for new users. Its internationalization capabilities ensure accessibility across different locales. See Frontend Application Development for more details.
The Agent Runtime is responsible for executing AI agents within isolated Docker environments. This isolation ensures security and consistency during agent operations such as browser automation, code interpretation, and system interactions. It allows agents to perform a range of tasks from web intelligence to file management without compromising the core system.
Database & Storage underpins the entire platform, utilizing Supabase for its authentication, data storage, and real-time monitoring capabilities. This layer manages all persistent data, including agent configurations, user profiles, billing information, and conversational histories. It incorporates robust security measures, such as Row-Level Security (RLS) policies, to enforce multi-tenancy and data isolation, ensuring that user data is protected and access controls are respected. See Database Management and Migrations for more details.
Together, these four components form a cohesive architecture that supports the development, management, and deployment of diverse AI agents, from general-purpose assistants to specialized automation tools, across web, mobile, and backend environments.

Python SDK for Programmatic Interaction
The Python SDK provides a programmatic interface for developers to build, manage, and interact with AI Workers on the Suna platform. This SDK, housed primarily within the sdk directory, allows for comprehensive agent lifecycle management, the creation and handling of conversational threads, and the seamless integration of various tools to extend agent capabilities.
Developers can leverage the SDK to create general-purpose assistants or specialized automation tools. The SDK is designed to abstract the complexities of direct API interaction, offering a higher-level client. For instance, the Kortix class in sdk/kortix/kortix.py serves as the primary entry point, providing simplified access to agent and thread management functionalities.
Agent lifecycle management encompasses the creation, retrieval, updating, and execution of AI agents. Through the SDK, developers can define an agent's system_prompt, configure its allowed_tools, and manage custom Message Control Plane (MCP) tools. For example, the Agent class in sdk/kortix/agent.py facilitates these operations, allowing an agent to be run within a conversational thread.
Conversational threads, managed by components like the Thread class in sdk/kortix/thread.py, enable structured interactions with AI agents. The SDK provides mechanisms to add messages to a thread, retrieve message history, and track agent runs, which represent the execution of an agent within a thread. Streaming capabilities are also built into the SDK, allowing real-time processing of agent responses. For example, the print_stream utility in sdk/kortix/utils.py can parse and format streaming output, including tool calls and messages, for console display.
Tool integration is a core aspect of the SDK, allowing AI agents to interact with external systems and data sources. The SDK supports both predefined AgentPressTools and dynamically discovered MCPTools. MCPTools, as defined in sdk/kortix/tools.py, connect to an MCP endpoint to discover and enable tools, thereby allowing agents to perform tasks like fetching weather information or interacting with other services, as demonstrated in the sdk/example/mcp_server.py example.
For a practical demonstration, the sdk/example directory contains a working example that showcases the programmatic creation of an agent, its configuration with tools provided by a local MCP server, and the management of a conversational thread. This example also illustrates how to persist agent and thread IDs using a simple key-value store, making it easier to run and re-run agent interactions. The full usage guidance and installation instructions are available in sdk/README.md.

API Layer and Type Definitions
The mobile application utilizes a centralized API layer for managing its interactions with the backend and Supabase services, as described in apps/mobile/api. This layer orchestrates API configuration, environment-specific URL resolution, authentication token handling, and Supabase client initialization with session persistence and automatic token refreshing.
Configuration for backend and frontend URLs is handled in apps/mobile/api/config.ts. This involves dynamically determining the appropriate backend API URL, which can vary based on the environment (e.g., development, staging, production) and specific platform (e.g., ios, Android). Similarly, the frontend URL is resolved for authentication redirects and sharing functionalities. This file also manages authentication headers by asynchronously fetching access tokens from Supabase and integrating them into API requests.
The Supabase client, which facilitates user authentication and data storage, is initialized and managed in apps/mobile/api/supabase.ts. This initialization ensures session persistence across app launches by leveraging @react-native-async-storage/async-storage. It also implements automatic token refreshing, which monitors the application's state and proactively refreshes authentication tokens when the app becomes active, thereby preventing expired sessions. For robustness, the system includes environment variable validation and provides a fallback mock client if Supabase credentials are not properly configured, allowing the application to function without crashing while indicating missing services.
All TypeScript interfaces for API models and responses are defined in apps/mobile/api/types.ts. This centralization of type definitions ensures consistent data structures across various domains, including chat and messages, projects, files and sandbox, AI agents and models, and triggers. These interfaces also cover common API patterns such as pagination, file uploads, and standardized error responses, supporting type safety throughout the application's interaction with its backend. The apps/mobile/api/index.ts file acts as a central re-export point, simplifying access to these configurations, types, and the Supabase client.
Global State Management
The mobile application manages application-wide state through a combination of React's Context API and the Zustand library. This approach allows various features to access and modify shared data without passing props manually through every component in the tree. Key areas where global state management is applied include user authentication, selection of AI agents and models, billing information, advanced feature toggles, language settings, user presence, and tracking consent.
The core implementation involves individual context providers for each domain. For instance, authentication state and actions such as signIn, signUp, and signOut are managed by an AuthContext within apps/mobile/contexts/AuthContext.tsx. Similarly, AgentContext in apps/mobile/contexts/AgentContext.tsx handles the currently selected AI agent and model, along with the list of available agents. Billing-related data, including subscription status and credit balance, is centralized in BillingContext in apps/mobile/contexts/BillingContext.tsx. Other contexts manage advanced feature flags (AdvancedFeaturesContext in apps/mobile/contexts/AdvancedFeaturesContext.tsx), the application's language (LanguageContext in apps/mobile/contexts/LanguageContext.tsx), user online/offline status and active threads (PresenceContext in apps/mobile/contexts/PresenceContext.tsx), and user consent for tracking (TrackingContext in apps/mobile/contexts/TrackingContext.tsx).
These context providers are aggregated and rendered at the root of the application by AppProviders in apps/mobile/providers/AppProviders.tsx, ensuring that their state and functionalities are available throughout the component tree. Many of these contexts integrate with AsyncStorage for persisting user preferences across app sessions, @tanstack/react-query for efficient data fetching and caching from external APIs, and Supabase for real-time updates and authentication.
In addition to the React Context API, Zustand stores are utilized for more granular state management of specific UI components. For example, the visibility and content of the pricing/billing modal are managed by usePricingModalStore (aliased as useBillingModalStore) in apps/mobile/stores/billing-modal-store.ts. Similarly, the useFeedbackDrawerStore in apps/mobile/stores/feedback-drawer-store.ts controls the state of the feedback drawer, including its visibility and user ratings. This hybrid approach allows for both broad application-level state distribution via Context API and localized, performant state management for specific UI elements with Zustand. Backend Services and AI Agent Management
The Suna platform's backend is implemented as a Python FastAPI application, served by Gunicorn, and is primarily responsible for managing AI agent lifecycles, user accounts, billing, and integrations with external services.
The application's core logic resides within the backend directory. The main entry point, backend/api.py, orchestrates the entire application, handling startup and shutdown processes to ensure resources like the database and Redis are properly initialized and released. This includes pre-loading AI tools, managing static configurations, and starting background tasks for metrics collection and memory monitoring. The API enforces security and performance through middleware for Cross-Origin Resource Sharing (CORS), rate limiting, and structured request logging. All API routes are organized using APIRouter instances, providing a modular structure for different functionalities such as AI agents, billing, and sandbox operations. System health checks are also integrated, offering endpoints to verify the status of the application and its dependencies, including Redis and the database.
Background agent execution is handled by a dramatiq worker, defined in backend/run_agent_background.py. This worker processes agent runs asynchronously, managing their complete lifecycle from initialization and configuration loading to processing responses and persisting results. It utilizes distributed locking to prevent duplicate executions, subscribes to Redis Pub/Sub channels for real-time stop signals, and streams responses back to clients as the agent operates. Error tracking and performance monitoring are integrated via Sentry, and a worker health check ensures Redis connectivity is maintained.
Deployment of the backend is managed through a multi-stage Dockerfile located at backend/Dockerfile. This Dockerfile builds a production-ready container image using a lightweight Alpine Linux base, uv for efficient dependency management, and Gunicorn with Uvicorn workers for high-performance ASGI application serving. The Gunicorn configuration is optimized for CPU-bound applications, and logging is directed to standard output for seamless integration with container orchestration systems. Instructions for launching both backend and frontend components, including redis and dramatiq workers, are provided in the backend/README.md.

AI Agent Lifecycle Management
AI agents within the Suna platform undergo a comprehensive lifecycle, encompassing their creation, configuration, versioning, import/export, and execution, with real-time updates and integration with background task processing.
Agents are defined with a name, a system_prompt that guides their behavior, and associated tools. Tools can be agentpress_tools for core functionalities, configured_mcps for Message Control Plane integrations, or custom_mcps for specialized functionalities. When an agent is created, the system checks against user-specific creation limits. The initial configuration is stored as the first version of the agent.
The platform supports agent versioning. Any modifications to an agent's fundamental configuration, such as its system_prompt or tool associations, automatically trigger the creation of a new version. This ensures that a complete history of an agent's capabilities and instructions is maintained, allowing for traceability and rollback if necessary. Agents can be updated, but there are restrictions on modifying "Suna default agents" to preserve the integrity of core functionalities. Deletion of an agent involves removing its record from the database and critically, cleaning up any associated triggers to prevent orphaned processes.
Agent configurations can be exported as JSON files, enabling sharing and backup. Conversely, agents can be imported from JSON. The import process includes an analysis step that identifies any missing credentials or custom configurations required for the imported agent to function correctly. This ensures that users are aware of prerequisites before a full import is attempted.
Agent execution is managed through a unified API endpoint that orchestrates the start of an agent run. This process involves billing checks, handling file uploads, ensuring a sandbox environment for execution, and dispatching the agent's tasks to a background worker. Real-time streaming updates from agent runs are facilitated through Redis Pub/Sub channels, allowing the frontend to display progress, messages, and tool calls as they occur. The execution process also manages stopping agent runs and retrieving their status. The backend also provides administrative functionalities to manage user accounts, including user listing, activity monitoring, and agent installation for users.
The core conversational AI framework, AgentPress, underpins agent execution. It manages interactions with Large Language Models (LLMs), handling context management, token counting, and various compression strategies to optimize context windows. AgentPress also orchestrates tool execution, prompt caching, and robust error handling during agent runs. AI models are centrally managed, defining their capabilities, pricing, and lifecycle. The system includes mechanisms for model resolution, usage validation, and cost calculation based on token consumption.
A comprehensive set of tools is available for AI agents, covering external data access, browser automation, image and document manipulation, knowledge base interaction, and secure shell command execution within a sandboxed environment. This extensive tooling allows agents to perform diverse and complex tasks.
The platform integrates with external services such as Composio for toolkit and trigger management, and Google services for Docs and Slides. It also provides mechanisms for securely managing multi-cloud provider credentials, allowing agents to interact with various external platforms. The system further includes robust knowledge base management functionalities, supporting file processing, summarization, and hierarchical organization of information. These backend services are orchestrated by a Python FastAPI application, served with Gunicorn, which also includes health checks to ensure system stability. Conversational AI Framework (AgentPress)
AgentPress is a framework that provides a structured approach to managing conversational AI agents. It orchestrates interactions with Large Language Models (LLMs), integrates various tools, and implements strategies for optimizing performance, cost, and context management during agent-driven conversations.
At its core, AgentPress manages the entire lifecycle of a conversation thread. This includes the persistence of messages, invocation of LLM APIs, and execution of tools. The ThreadManager in backend/core/agentpress/thread_manager.py is central to these operations, handling the flow of dialogue, managing auto-continuation of multi-turn conversations, and integrating with other components for comprehensive agent functionality.
A critical aspect of AgentPress is its approach to context management, which is handled by the ContextManager in backend/core/agentpress/context_manager.py. This component is designed to manage token usage and prevent exceeding the context window of LLMs. It achieves this through accurate token counting for different LLM providers, intelligent message grouping, and tiered compression strategies. These strategies can involve in-memory content compression, deterministic truncation, and the omission of entire message groups from the middle of the conversation to retain recent and initial context.
AgentPress also incorporates a prompt caching system, detailed in backend/core/agentpress/prompt_caching.py. This system is optimized for Anthropic models and dynamically calculates cache thresholds based on conversation stage, context size, and token density. It aims to reduce token consumption and latency by reusing cached prompt blocks, especially for system prompts and tool definitions. The system ensures that tool call sequences are treated as atomic units for caching, preserving conversational flow.
Tool execution is another key feature, facilitated by the ResponseProcessor in backend/core/agentpress/response_processor.py. This processor handles both streaming and non-streaming LLM responses, detecting and parsing tool calls in various formats (e.g., XML-based or native OpenAI-style). It orchestrates the execution of these tools by looking up registered functions in a ToolRegistry (defined in backend/core/agentpress/tool.py) and invoking them with the provided arguments. This allows agents to perform actions like data retrieval, browser automation, or interacting with external services. The ResponseProcessor also manages message formatting and persistence, ensuring that all interactions are recorded.
Robust error handling is integrated into AgentPress, with the ErrorProcessor in backend/core/agentpress/error_processor.py providing a unified mechanism for processing, standardizing, and logging errors. This component abstracts away the specifics of different exception types, particularly those originating from LLM interactions via litellm, into a consistent ProcessedError structure for logging and user-facing messages.
AgentPress supports various types of tool calls, including native OpenAI-style tool calls, which are parsed by native_tool_parser in backend/core/agentpress/native_tool_parser.py. This component extracts, validates, and converts tool call data from LLM responses, handling streaming chunks and partial JSON arguments to ensure proper tool execution.
AI Model Management and Cost Calculation
The Suna platform incorporates a dedicated system for defining, registering, and managing artificial intelligence models, including their capabilities, pricing, and operational lifecycle. This system facilitates the integration of various AI model providers and ensures that models are appropriately selected and utilized based on requirements and user access tiers.

This metadata includes details such as the model's unique identifier, its human-readable name, the provider (e.g., OpenAI, Anthropic, Bedrock, Google), a list of associated aliases, context window size, maximum output tokens, and specific capabilities like chat, function calling, vision, or code interpretation. Each model also has pricing information, detailing input and output token costs, and flags indicating if it's enabled, in beta, or recommended. The manager can resolve various model identifiers, including internal IDs, aliases, and provider-specific IDs (such as Bedrock ARNs for LiteLLM integration), ensuring flexibility in how models are referenced. It also includes logic to select the best available model based on criteria like user tier, required capabilities, and context window size, with an option to prioritize cheaper models. The ModelManager also supports checking token limits to ensure that requested input and output tokens do not exceed a model's capabilities, helping to prevent errors and optimize resource usage. The aggregation of these components within the backend/core/ai_models directory provides a comprehensive framework for AI model management and cost calculation, crucial for the Suna platform's operational efficiency and economic transparency.

Internationalization and Localization
The internationalization strategy of the Suna platform's frontend focuses on providing a localized experience across web and mobile applications, with a robust system for locale detection, translation management, and routing. Supported locales, including English, German, Italian, Chinese, Japanese, Portuguese, French, and Spanish, are defined and managed within frontend/src/i18n/config.ts. English is set as the default locale, serving as a fallback when other language preferences are unavailable or unsupported.
Locale detection is a multi-tiered process that prioritizes user preferences for an optimal experience. The system first checks for an explicit locale setting in the user's profile metadata, followed by a locale cookie, and then a locale specified in the URL path or an x-locale header. If no explicit preference is found, the system attempts to infer the locale from the browser's accept-language header. As a final fallback, the defaultLocale is used. This cascading approach, primarily handled by getRequestConfig in frontend/src/i18n/request.ts, ensures that content is delivered in the most appropriate language for the user.
For marketing pages, the system employs geo-detection and URL-based routing to provide localized content. The middleware in frontend/src/middleware.ts plays a crucial role by intercepting requests. For marketing routes, it checks for locale prefixes (e.g., /de/suna). If a valid prefix is present, the URL is rewritten internally to remove the prefix, and the detected locale is set via a cookie and x-locale header for downstream internationalization libraries. If no locale prefix is found, the middleware attempts to detect the best locale based on the accept-language header. If a non-default locale is detected and the user has no explicit preference, the system redirects the user to the locale-prefixed version of the URL, enhancing discoverability of localized content. The I18nProvider component in frontend/src/components/i18n-provider.tsx further manages client-side internationalization by dynamically loading translation files and persisting locale preferences across sessions and browser tabs.

Tool Integration and Management
The Suna SDK facilitates the integration of diverse tools for AI agents, allowing them to extend their capabilities beyond basic conversational functions. This integration primarily involves two categories of tools: predefined functionalities accessible through AgentPressTools and dynamically discovered tools managed by MCPTools.
AgentPressTools provides a fixed enumeration of commonly used tools, each with a predefined, human-readable description. These are standard functionalities, such as file manipulation, web browsing, or shell execution, that an agent can leverage. The SDK defines these using an Enum in sdk/kortix/tools.py, ensuring type safety and a clear, explicit list of capabilities.
Conversely, MCPTools enables agents to discover and utilize tools dynamically from a Message Control Plane (MCP) service. This is particularly useful for integrating with external microservices or custom functionalities. The MCPTools class in sdk/kortix/tools.py initializes a client to an MCP endpoint, fetches available tools from it, and allows for filtering based on an allowed list. The asynchronous initialize method is crucial for connecting to the MCP service and discovering tools without blocking the application. An example of a local MCP server that exposes tools is provided in sdk/example/mcp_server.py, showcasing how custom tools can be made available to agents.
Agents are configured to utilize these tools during their creation or update process. When an agent is created or modified via the KortixAgent class in sdk/kortix/agent.py, its configuration can include both AgentPressTools and MCPTools. The update and create methods handle the intelligent configuration of agentpress_tools and custom_mcps, enabling or disabling tools based on the allowed_tools specified. The AgentsClient in sdk/kortix/api/agents.py is responsible for the API interactions that manage an agent's tool configurations, including fetching available tools and updating custom MCP tool settings. The SDK provides a unified KortixTools type alias, defined in sdk/kortix/tools.py, to abstract whether a tool originates from AgentPressTools or MCPTools, simplifying type hinting and generic tool handling.
An example in sdk/example/example.py demonstrates how to set up an AI agent with tool integration. This includes initializing kortix.Kortix and kortix.MCPTools clients, creating or updating an agent with specific allowed_tools, and running the agent to process a query that might invoke these tools. The output from such agent runs, including tool calls and results, is processed and displayed using the print_stream utility from sdk/kortix/utils.py. The print_stream function provides formatted, colored output, reconstructing messages and highlighting tool calls from the agent's execution stream. This allows developers to observe the agent's decision-making process and its interaction with the configured tools. Streaming and Output Processing
The Suna SDK provides mechanisms for handling real-time data from AI agent runs, enabling developers to process and display continuous streams of information. Central to this functionality is the stream_from_url utility and the advanced print_stream function.
The stream_from_url utility, found in sdk/kortix/api/utils.py, is an asynchronous generator that fetches data from a specified URL and yields its content line by line. This is particularly useful for consuming streaming APIs or large text files efficiently without buffering the entire content. It leverages the httpx library for asynchronous HTTP requests, employing a robust timeout configuration to prevent interruptions during long streaming operations.
Building upon this, the print_stream function, located in sdk/kortix/utils.py, processes the raw stream data into formatted, human-readable output. This asynchronous generator interprets different event types from the stream, such as status updates, assistant messages, and tool calls. It reconstructs full messages from potentially fragmented chunks, applies syntax highlighting to embedded XML content, and color-codes the output for enhanced readability in the console. This function is crucial for developers to observe the real-time progression of an AI agent's thought process, tool utilization, and responses. The print_stream function also detects and highlights function calls, enabling a clear view of when the agent is invoking external tools.

Upon receiving a valid code, the system interacts with Supabase to establish a user session. If this exchange is unsuccessful, users are redirected with appropriate error notifications.
Following a successful session establishment, the system performs several post-login updates crucial for user management and personalized experiences. If a pending-referral-code is detected from cookies, the user's account is updated with this referral code, and the cookie is subsequently cleared. Additionally, if the user has accepted the terms and conditions during the authentication flow and this acceptance hasn't been recorded, the user's metadata is updated with a terms_accepted_at timestamp. The system also verifies the user's account initialization status, redirecting to a setup page if necessary, or to the dashboard if the account is fully configured. This sequence ensures that new users are properly onboarded and that their account details are accurately maintained before they access the platform. For a deeper understanding of user authentication methods, refer to Core Authentication Actions and Flows.

Password Reset Mechanism
The platform's password reset mechanism allows users to securely regain access to their accounts. This process involves a client-side interface for users to enter and confirm a new password, along with server-side logic that validates the reset code received via email and updates the user's credentials.
The user initiates a password reset request via the client-side interface provided by the primary authentication page. See Core Authentication Actions and Flows for more information. After the user provides their email, a server action, defined in frontend/src/app/auth/actions.ts, sends a password reset link to that email address. This link directs the user to a dedicated password reset page, implemented by frontend/src/app/auth/reset-password/page.tsx.
Upon arriving at the reset page, the system extracts a unique reset code from the URL parameters. The client-side component then validates the presence of this code and displays an error message if it's missing or invalid. If a valid code is found, the user is presented with a form to input and confirm their new password.
When the user submits the new password, another server action, also from frontend/src/app/auth/actions.ts, is invoked. This action securely updates the user's password in the backend. User feedback is provided throughout this process; a success message is displayed upon a successful password update, prompting the user to sign in, while error messages are shown for any issues encountered during validation or the update process. The use of React's Suspense ensures a smooth loading experience while the necessary data, such as search parameters, is being fetched.
